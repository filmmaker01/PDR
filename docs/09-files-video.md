# 09. Файлы, фотографии, видео

## Файловое хранилище

- Один приватный S3-совместимый bucket на окружение. Публичного доступа нет; все операции — через presigned URL с коротким сроком.
- Ключи: `<scope>/<workspace_id|user_id>/<yyyy>/<mm>/<file_id>.<ext>`; варианты: `<...>/<file_id>.thumb.webp`, `<file_id>.preview.webp`.
- Метаданные и статус — в таблице `files`; объект без записи в `files` считается мусором.

### Загрузка (клиент → S3 напрямую)

1. `POST /files/presign-upload` с `scope`, `workspaceId` (для CRM), `mimeType`, `sizeBytes`. Сервер проверяет: право на scope (участник мастерской / ученик с открытым этапом / админ), лимиты (`image ≤ 20 МБ`, `video ≤ 500 МБ` для сдач, длительность видео проверяется после загрузки), разрешённые типы (`image/jpeg, image/png, image/heic, image/webp, video/mp4, video/quicktime`, для материалов — `pdf`). Создаёт `files(status=pending)` и возвращает presigned PUT (или multipart для > 50 МБ: `createMultipartUpload` + presigned URL частей по 10 МБ).
2. Клиент грузит с прогрессом; при обрыве повторяет незавершённые части (multipart) или весь файл (PUT) — presign действует 10 минут, при истечении запрашивается заново с тем же `fileId`.
3. `POST /files/:id/complete` → сервер проверяет `HEAD` объекта (размер совпадает), ставит `uploaded`, ставит задачу `files.process`.
4. Worker: скачивает объект, проверяет magic bytes (тип соответствует заявленному), для изображений — EXIF-ориентация, миниатюра 400px и preview 1600px (sharp, webp), удаление EXIF-геометки из вариантов; для видео — `ffprobe` (длительность, размеры), кадр-превью; статус `ready`. Ошибка → `failed` с причиной, клиент показывает «Повторить».
5. Файл привязывается к сущности (`order_photos`, `submission_files`, …) в момент подтверждения; можно привязать сразу при `complete` (передать `attachTo`), чтобы не оставлять сирот.

HEIC с iPhone: конвертируется worker'ом в JPEG для вариантов; оригинал сохраняется.

### Выдача

- `GET /files/:id/url?variant=` → проверка доступа по привязке → presigned GET на 5 минут. В списках (фото заказа, галерея сдачи) сервер возвращает URL миниатюр пачкой в ответе, чтобы не делать N запросов; клиент кеширует до `expiresAt`.
- Прямых постоянных ссылок нет. Ссылка не содержит идентификаторов другой мастерской; подпись привязана к ключу объекта.

### Удаление и хранение

- Удаление фото заказа — мягкое (`files.deleted_at`) с физическим удалением через 30 дней worker'ом; версионирование bucket даёт дополнительное окно восстановления.
- Анонимизация клиента фото не удаляет (документация ремонта); отдельное действие «удалить фото заказов клиента».
- Файлы экспорта удаляются через 7 дней.
- Квоты: мягкий лимит на мастерскую (например 20 ГБ) с предупреждением владельцу в настройках; жёсткий лимит не применяется в 1.0, но объём учитывается (`sum(size_bytes)` по workspace) и виден администратору.

## Видео уроков

Требования: приватность (нельзя открыть по прямой ссылке), контроль доступа нашим сервером, адаптивное качество, работа в WebView Telegram на iOS/Android/Desktop, сохранение позиции.

Реализация — внешняя видеоплатформа за интерфейсом:

```ts
interface VideoProvider {
  createUpload(input: { title: string }): Promise<{ providerVideoId: string; uploadUrl: string } | { providerVideoId; instructions }>;
  getStatus(providerVideoId: string): Promise<{ status: 'processing'|'ready'|'failed'; durationSec?: number }>;
  issuePlayback(providerVideoId: string, opts: { userId: string; ttlSec: number }): Promise<{ embedUrl?: string; hlsUrl?: string; token?: string; expiresAt: Date }>;
  delete(providerVideoId: string): Promise<void>;
}
```

Требования к провайдеру (проверяются при выборе, до начала этапа 3 roadmap): приватные видео, подписанные/временные ссылки воспроизведения или токен плеера, ограничение по домену встраивания, API загрузки, HLS. **Выбран Kinescope** (приватные видео, защищённый плеер с подписанными ссылками, API загрузки, HLS, ориентирован на РФ). Реализация — `KinescopeProvider`; `MockVideoProvider` используется в тестах и в local-окружении без ключей, поэтому разработка не блокируется доступом к аккаунту.

Поток:

1. Админ в редакторе урока загружает видео → `POST /admin/videos` → `video_assets(status=uploading)` + URL загрузки у провайдера (браузер грузит напрямую). Worker опрашивает статус (или принимает webhook провайдера) → `ready`.
2. Ученик открывает урок → сервер проверяет `StageAccess` и грант → `issuePlayback` с TTL 2 часа → клиент получает `embedUrl`/`hlsUrl`. Плеер провайдера (iframe) или `hls.js` в собственном плеере. Предпочтение — собственный плеер на `hls.js` с нативным HLS на iOS, чтобы контролировать сохранение позиции и события просмотра; iframe провайдера — запасной вариант, если его защита работает только через свой плеер.
3. Клиент шлёт `progress` (позиция, максимальный процент) каждые 10 с и при паузе/закрытии (`navigator.sendBeacon` при уходе).

Учебные короткие видео учеников (сдачи) хранятся в нашем S3, не на видеоплатформе: они приватные, небольшие и смотрятся один-два раза куратором; воспроизводятся по presigned URL (`video/mp4`, `h264`), при необходимости worker перекодирует `.mov` в `mp4` через ffmpeg.

## Оценка объёмов (для выбора тарифов провайдеров)

| Что | Оценка на пилот (10 мастеров, 1 группа 20 учеников) |
|-----|------------------------------------------------------|
| Фото заказов | 10 мастеров × 40 заказов/мес × 15 фото × 3 МБ ≈ 18 ГБ/мес + варианты ≈ 20 ГБ/мес |
| Медиа сдач | 20 учеников × 15 заданий × (5 фото × 3 МБ + 1 видео × 60 МБ) ≈ 22 ГБ за курс |
| Видео курса | 3 этапа × 15 уроков × 15 минут в 1080p ≈ 11 часов исходников; трафик просмотра ≈ 20 учеников × 11 ч × ~1.5 ГБ/ч ≈ 330 ГБ на поток |

Цифры — рабочая оценка для расчёта, уточняются по реальному использованию.

## Реализация (этап 3)

- `StorageProvider` — единый интерфейс с двумя реализациями: `S3StorageProvider` (staging и production) и `LocalStorageProvider` (разработка и тесты без Docker). Локальный драйвер эмулирует подписанные ссылки собственным эндпоинтом с HMAC-подписью ключа, операции и срока, поэтому поведение клиента одинаково в обоих случаях. На staging и production `STORAGE_DRIVER=local` отклоняется проверкой конфигурации при старте.
- Загрузка идёт напрямую в хранилище: сервер выдаёт подписанную ссылку, зафиксировав в подписи тип и длину, и никогда не пропускает тело файла через себя. Файлы больше 50 МБ загружаются частями по 10 МБ.
- Тип файла определяется по сигнатуре (`detectFileType`), а не по заявленному `Content-Type`: файл с заголовком ELF, названный `image/png`, отбраковывается, объект удаляется, запись переводится в `failed`. Реализация собственная — набор принимаемых типов невелик, а библиотека `file-type` существует только в ESM и не подходит для CommonJS-сборки Nest.
- Подтверждение загрузки сверяет фактический размер объекта с заявленным; расхождение — отказ.
- Обработка в worker'е: контрольная сумма, миниатюра 400px и предпросмотр 1600px в WebP, поворот по EXIF и удаление метаданных из производных (в том числе геометок). HEIC с айфона конвертируется в WebP для просмотра, оригинал сохраняется.
- Доступ к файлу определяется его привязкой, а не типом: `FileAccessRegistry` хранит проверку на каждый scope, по умолчанию — запрет. Фото заказа доступно активным участникам мастерской-владельца; администратор платформы доступа к ним не имеет.
- Ссылки короткоживущие (5 минут). Подпись привязана к ключу объекта: подмена ключа в ссылке отклоняется, истёкшая ссылка не работает.
- Клиентская очередь (`useUploadQueue`) грузит файлы по одному, показывает прогресс, повторяет до трёх раз и запрашивает новую ссылку, если прежняя истекла, — уже загруженные файлы при этом не теряются.
- Уборка: незавершённые загрузки старше суток удаляются вместе с объектами, файлы, удалённые более 30 дней назад, стираются окончательно.
