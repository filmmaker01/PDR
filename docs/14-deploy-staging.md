# Публичный staging на Amvera: схема и порядок запуска

Документ описывает, как поднять staging по HTTPS, доступный с любого
устройства, без администрирования сервера. Описание инфраструктуры лежит в
репозитории: `amvera.yml`, `infra/docker/Dockerfile.amvera`,
`infra/docker/amvera-entrypoint.sh`, `infra/nginx/`.

## 1. Схема

**Amvera Cloud, три проекта из одного репозитория и управляемая PostgreSQL.**
Amvera читает `amvera.yml` из корня репозитория и пересобирает приложение при
каждом push в привязанную ветку.

| Компонент | Как размещён |
|---|---|
| PostgreSQL 16 | управляемая СУБД Amvera |
| API | проект `pdr-api`, Docker |
| Worker | **в том же процессе, что API** |
| Mini App | проект `pdr-app`, тот же образ, nginx отдаёт статику |
| Админка | проект `pdr-admin`, тот же образ |
| Файлы | постоянное хранилище проекта `/data` |
| Миграции | `prisma migrate deploy` при старте контейнера |
| Demo-данные | сидер при старте, **только если база пуста** |
| HTTPS | бесплатный домен Amvera с сертификатом |

### Почему один образ на все три приложения

В Amvera один репозиторий даёт один файл конфигурации в корне, а каждое
приложение — это отдельный проект. Собрать из одного репозитория три разных
образа с разными настройками там негде: все проекты прочитают один и тот же
`amvera.yml`.

Поэтому образ собирается один — с API, worker и обоими собранными
фронтендами, — а что именно запускать, решает переменная окружения
`PROCESS_ROLE` в настройках каждого проекта:

| Проект | `PROCESS_ROLE` | Что делает |
|---|---|---|
| `pdr-api` | `api` | миграции, демо-данные, API, фоновые задачи |
| `pdr-app` | `miniapp` | nginx отдаёт `/srv/miniapp` |
| `pdr-admin` | `admin` | nginx отдаёт `/srv/admin` |

Приложение при этом не меняется: код тот же самый, разница только в том,
какой процесс стартует.

### Почему адрес API подставляется при старте, а не при сборке

Amvera не пробрасывает переменные окружения в этап сборки. Адрес API попадает
в бандл фронтенда именно при сборке, поэтому в образ он вшивается
плейсхолдером `__PDR_API_URL__`, а `entrypoint` заменяет его на значение
переменной `API_URL` перед запуском nginx.

Практический эффект: сменить домен — это изменить переменную окружения в
интерфейсе Amvera и перезапустить приложение. Пересобирать образ и что-то
править в репозитории не нужно.

### Почему worker не отдельный проект

Постоянное хранилище `/data` принадлежит проекту. Отдельный worker не видел бы
файлы, загруженные через API: он делает миниатюры и собирает выгрузки. Поэтому
на staging API и обработчик задач живут в одном процессе (`WORKER_ROLE=true`).

Когда подключим S3, worker выносится в четвёртый проект с тем же образом и
`PROCESS_ROLE=worker` — entrypoint это уже умеет.

## 2. Что нужно от вас

1. **Аккаунт Amvera** (amvera.ru), пополненный баланс. Оплата рублёвыми
   картами.
2. **Токен доступа GitHub** — чтобы Amvera читал приватный репозиторий.
3. **Домен** — не обязателен. Без него адреса будут вида
   `pdr-app.<ваш-логин>.amvera.io` с бесплатным HTTPS.

Секреты в репозиторий не попадают: они задаются переменными окружения в
интерфейсе Amvera.

## 3. Порядок действий

### Шаг 1. Влить ветку

`amvera.yml` должен быть в той ветке, которую вы привяжете к проектам.
Смержите `claude/sleepy-hamilton-atoayb` в `main`.

### Шаг 2. Создать базу данных

Amvera → **Создать проект** → тип **База данных** → **PostgreSQL**, версия 16.
Задайте пользователя и пароль. После создания на вкладке «Информация»
скопируйте **внутреннее доменное имя** вида
`amvera-<логин>-cnpg-<имя-проекта>-rw`.

Строка подключения для приложения:

```
postgresql://<пользователь>:<пароль>@amvera-<логин>-cnpg-<имя>-rw:5432/<база>?schema=public
```

Если приложение не сможет подключиться из-за TLS, добавьте в конец
`&sslmode=disable` (внутри сети Amvera трафик и так не выходит наружу).

### Шаг 3. Создать проект `pdr-api`

**Создать проект** → **Приложение** → тип окружения **Docker** → привязать
репозиторий GitHub (токен + ветка). Переменные окружения:

| Переменная | Значение |
|---|---|
| `PROCESS_ROLE` | `api` |
| `NODE_ENV` | `production` |
| `APP_ENV` | `staging` |
| `PORT` | `3000` |
| `DATABASE_URL` | строка подключения из шага 2 |
| `PUBLIC_API_URL` | адрес этого проекта, например `https://pdr-api.<логин>.amvera.io` |
| `MINIAPP_URL` | адрес Mini App |
| `ADMIN_URL` | адрес админки |
| `SESSION_JWT_SECRET` | `openssl rand -base64 48` |
| `DEMO_LOGIN_ENABLED` | `true` |
| `DEMO_LOGIN_SECRET` | своя строка не короче 16 символов |
| `RUN_MIGRATIONS_ON_BOOT` | `true` |
| `SEED_DEMO_ON_EMPTY` | `true` |
| `WORKER_ROLE` | `true` |
| `STORAGE_DRIVER` | `local` |
| `STORAGE_LOCAL_DIR` | `/data/storage` |
| `VIDEO_PROVIDER` | `mock` |
| `TELEGRAM_ENABLED` | `false` |
| `LOG_LEVEL` | `info` |

Адреса фронтендов заранее неизвестны — впишите предполагаемые
(`https://pdr-app.<логин>.amvera.io`, `https://pdr-admin.<логин>.amvera.io`) и
поправьте после шага 5, если Amvera выдаст другие.

Затем **Настройки** → **Доменные имена** → добавить бесплатный домен Amvera.

### Шаг 4. Создать проекты `pdr-app` и `pdr-admin`

Тот же репозиторий и та же ветка, тип окружения **Docker**. Переменные:

| Переменная | `pdr-app` | `pdr-admin` |
|---|---|---|
| `PROCESS_ROLE` | `miniapp` | `admin` |
| `API_URL` | адрес `pdr-api` | адрес `pdr-api` |

Каждому — бесплатный домен Amvera.

### Шаг 5. Свести адреса

Когда все три домена выданы, проверьте, что в `pdr-api` переменные
`PUBLIC_API_URL`, `MINIAPP_URL`, `ADMIN_URL` указывают на настоящие адреса, а
в `pdr-app` и `pdr-admin` переменная `API_URL` — на настоящий адрес API.
После правки перезапустите приложения. Пересборка не нужна.

Проверка: `https://<адрес API>/health/ready` должен отдать `{"status":"ok"}`.

### Шаг 6. Войти

Mini App: `https://<адрес Mini App>/?demo=<DEMO_LOGIN_SECRET>` — появится экран
выбора роли. Секрет запоминается в браузере, дальше достаточно обычного
адреса. Админка: `https://<адрес админки>`, демо-кнопки внизу формы входа.

## 4. Что проверить после первого деплоя

| Что | Где смотреть |
|---|---|
| Образ собрался | логи сборки проекта |
| Миграции прошли | в логах `All migrations have been successfully applied` |
| Демо-данные залиты | в логах сводка и список ключей демо-аккаунтов |
| API отвечает | `/health/ready` → `"status":"ok"` |
| Фронтенд знает адрес API | в логах `[entrypoint] подставляю API_URL=...` |

Места, где первый деплой может споткнуться:

- **Расширение `btree_gist`.** Миграция календаря создаёт его сама. Управляемая
  PostgreSQL Amvera построена на CloudNativePG, где стандартные contrib-модули
  есть, но если платформа его не разрешит — миграция упадёт с понятной ошибкой
  в логе.
- **TLS при подключении к базе.** Если Prisma ругается на SSL, добавьте
  `&sslmode=disable` к `DATABASE_URL`.
- **Размер образа.** В образе лежат API, оба фронтенда и полный
  `node_modules` (включая `prisma` и `tsx` — они нужны для миграций и сидера).
  Ориентировочно 1,5–2 ГБ; если тариф по диску не вмещает, берите следующий.
- **Память.** На минимальном тарифе 0,1 ГБ ОЗУ — этого мало для Node с Prisma.
  Для `pdr-api` берите тариф с 1 ГБ и выше; фронтендам хватает минимального,
  там работает только nginx.
- **HTTPS обязателен для API.** Политика CSP фронтендов разрешает запросы
  только по `https:`. На бесплатном домене Amvera сертификат выдаётся сам, но
  по `http://` приложение работать не будет.

## 5. Ограничения этого staging

1. Telegram выключен: вход только демо-аккаунтами, уведомления и напоминания
   не отправляются.
2. Видео — заглушка вместо плеера.
3. Файлы лежат в `/data` проекта `pdr-api`.
4. Резервное копирование базы — средствами Amvera, скрипты из `infra/backup`
   на управляемую СУБД не рассчитаны.

## 6. Следующий этап

Подключение Telegram, Kinescope, S3 и закрытой группы — это переменные
окружения, продукт менять не нужно:

| Что включаем | Переменные |
|---|---|
| Telegram | `TELEGRAM_ENABLED=true`, `TELEGRAM_BOT_TOKEN`, `TELEGRAM_BOT_USERNAME`, `TELEGRAM_WEBHOOK_SECRET` |
| Клуб | `TELEGRAM_CLUB_CHAT_ID`, `TELEGRAM_CLUB_INVITE_LINK` |
| Kinescope | `VIDEO_PROVIDER=kinescope`, `KINESCOPE_API_KEY`, `KINESCOPE_PARENT_ID` |
| S3 | `STORAGE_DRIVER=s3`, `S3_ENDPOINT`, `S3_BUCKET`, `S3_ACCESS_KEY`, `S3_SECRET_KEY` |

Имя бота попадает в админку так же, как адрес API: плейсхолдером при сборке и
подстановкой из переменной `BOT_USERNAME` при старте.

Вместе с S3 worker выносится в отдельный проект (`PROCESS_ROLE=worker`,
`WORKER_ROLE` на API убирается), и демо-вход можно выключить
(`DEMO_LOGIN_ENABLED=false`).
