# Публичный staging: схема и порядок запуска

Документ описывает, как поднять staging по HTTPS, доступный с любого
устройства, без администрирования сервера. Всё описание инфраструктуры лежит
в репозитории: `render.yaml`, `infra/docker/Dockerfile.api`,
`infra/docker/entrypoint.sh`.

## 1. Схема

**Render.com, один Blueprint.** Файл `render.yaml` в корне репозитория
описывает всю инфраструктуру; Render читает его из GitHub и создаёт ресурсы
сам. Каждый push в ветку пересобирает и выкладывает изменившиеся части.

| Компонент | Как размещён |
|---|---|
| PostgreSQL 16 | управляемая база Render |
| API | Docker-контейнер из `infra/docker/Dockerfile.api` |
| Worker | **в том же процессе, что API** (`WORKER_ROLE=true`) |
| Mini App | статический сайт, собирается из `apps/miniapp` |
| Админка | статический сайт, собирается из `apps/admin` |
| Файлы | диск контейнера (`STORAGE_DRIVER=local`) |
| Миграции | `prisma migrate deploy` при старте контейнера |
| Demo-данные | сидер при старте, **только если база пуста** |
| HTTPS | сертификаты Render, автоматически |

Почему Render, а не VPS с `docker compose` (он в репозитории тоже есть,
`infra/docker/compose.deploy.yml`): compose требует заранее поднятый и
настроенный сервер — установить Docker, положить `.env`, настроить Caddy,
следить за обновлениями ОС. Blueprint не требует ничего: подключается
репозиторий, нажимается «Apply».

### Почему worker не отдельный сервис

Пока файлы лежат на диске, а не в S3, диск монтируется ровно к одному
сервису. Отдельный worker не видел бы загруженные снимки: он делает
миниатюры и собирает выгрузки. Поэтому на staging API и обработчик задач
живут в одном процессе — код один и тот же (`AppModule`), меняется только
переменная `WORKER_ROLE`.

Когда подключим S3, worker выносится в отдельный сервис: на API ставится
`WORKER_ROLE=false`, в `render.yaml` раскомментируется блок в конце файла.

## 2. Сколько стоит

| Вариант | Что получается | Цена |
|---|---|---|
| **Free** (по умолчанию в `render.yaml`) | всё работает, но API засыпает после 15 минут простоя (первый запрос ~1 мин), база живёт 30 дней, постоянного диска нет — загруженные файлы исчезают при перезапуске | $0 |
| **Starter** | без засыпания, постоянная база и диск | ≈ $7 (API) + $6 (база) + $0.25/ГБ (диск) в месяц |

Начать можно с free и переключиться, не меняя ничего, кроме двух строк
`plan:` и блока `disk:`.

## 3. Что нужно от вас

1. **Аккаунт GitHub** — уже есть, репозиторий `filmmaker01/PDR`.
2. **Аккаунт Render** — регистрация на render.com через GitHub, карта не
   нужна для free.
3. **Домен** — не обязателен. Без него адреса будут вида
   `pdr-app.onrender.com`. Если домен есть, понадобится доступ к его
   DNS-записям.

Ничего передавать мне не нужно: пароли и секреты Render генерирует сам и
хранит у себя, в репозиторий они не попадают.

## 4. Порядок действий

### Шаг 1. Влить ветку

`render.yaml` должен быть в ветке, из которой Render будет собирать.
Смержите `claude/sleepy-hamilton-atoayb` в `main` (или укажите ветку при
подключении Blueprint).

### Шаг 2. Создать Blueprint

1. render.com → **New** → **Blueprint**.
2. Подключить GitHub, выбрать репозиторий `filmmaker01/PDR` и ветку.
3. Render покажет, что создаст: база `pdr-staging-db` и три сервиса
   `pdr-api`, `pdr-app`, `pdr-admin`. Нажать **Apply**.

Первая сборка занимает 5–10 минут: собирается Docker-образ API и обе
статики.

### Шаг 3. Записать адреса и поправить их в `render.yaml`

После создания Render покажет реальные адреса сервисов. Если имена были
свободны, это будет ровно то, что уже записано в `render.yaml`:

```
https://pdr-api.onrender.com
https://pdr-app.onrender.com
https://pdr-admin.onrender.com
```

Если Render добавил суффикс (имя было занято), откройте `render.yaml`,
замените адреса в блоке «ЗАМЕНИТЬ ЗДЕСЬ» и во всех местах, где они
встречаются, и запушьте. Передеплой произойдёт сам.

Проверка: `https://<адрес API>/health/ready` должен отдать
`{"status":"ok"}`.

### Шаг 4. Взять секрет демо-входа

Render → сервис `pdr-api` → **Environment** → значение `DEMO_LOGIN_SECRET`.

Открыть Mini App: `https://<адрес Mini App>/?demo=<секрет>` — появится
экран выбора роли. Секрет запоминается в браузере, дальше достаточно
обычного адреса. Админка: `https://<адрес админки>`, демо-кнопки внизу
формы входа.

### Шаг 5 (если есть домен). Свои адреса

1. В Render на каждом сервисе: **Settings** → **Custom Domains** → добавить
   `api.<домен>`, `app.<домен>`, `admin.<домен>`.
2. В DNS домена создать CNAME-записи, которые покажет Render.
3. В `render.yaml` заменить три адреса на свои и запушить.
4. Пока DNS обновляется, оба адреса можно держать рабочими: перечислите
   старые в `CORS_EXTRA_ORIGINS` через запятую.

## 5. Что проверить после первого деплоя

| Что | Где смотреть | Если не так |
|---|---|---|
| API поднялся | `/health/ready` → `"status":"ok"` | логи `pdr-api` в Render |
| Миграции прошли | в логах `All migrations have been successfully applied` | см. ниже про `btree_gist` |
| Демо-данные залиты | в логах строка со сводкой и списком ключей | база была не пуста — это нормально |
| Фронтенды собрались | адреса открываются | логи сборки статики |
| Вход работает | экран выбора роли по ссылке с `?demo=` | проверьте `DEMO_LOGIN_SECRET` |

Три места, где первый деплой может споткнуться, и что делать:

- **`SESSION_JWT_SECRET` короче 32 символов.** Render генерирует значение
  сам, но проверка конфигурации требует длину ≥ 32. Если API падает с
  сообщением про секрет — впишите в Environment значение
  `openssl rand -base64 48`.
- **Расширение `btree_gist`.** Миграция календаря создаёт его сама
  (`CREATE EXTENSION IF NOT EXISTS btree_gist`). Это стандартное расширение
  PostgreSQL, но если хостинг его не разрешит, миграция упадёт с понятной
  ошибкой в логе — тогда расширение включается через настройки базы.
- **Память на free-плане.** 512 МБ. Если в логах появится OOM при обработке
  фотографий — переключите `plan: free` на `plan: starter` у `pdr-api`.

## 6. Ограничения этого staging

1. Telegram выключен: вход только демо-аккаунтами, уведомления и
   напоминания не отправляются.
2. Видео — заглушка вместо плеера.
3. Файлы на диске контейнера. На free-плане диска нет вовсе: загруженное
   исчезает при перезапуске, демо-данные создаются заново.
4. На free-плане API засыпает после 15 минут простоя, поэтому регулярные
   фоновые задачи (напоминания, истечение доступов) выполняются
   нерегулярно.
5. Резервных копий базы на free-плане нет.

## 7. Следующий этап

Подключение Telegram, Kinescope, S3 и закрытой группы — отдельно. В
`render.yaml` это переменные окружения, продукт менять не нужно:

| Что включаем | Переменные |
|---|---|
| Telegram | `TELEGRAM_ENABLED=true`, `TELEGRAM_BOT_TOKEN`, `TELEGRAM_BOT_USERNAME`, `TELEGRAM_WEBHOOK_SECRET` |
| Клуб | `TELEGRAM_CLUB_CHAT_ID`, `TELEGRAM_CLUB_INVITE_LINK` |
| Kinescope | `VIDEO_PROVIDER=kinescope`, `KINESCOPE_API_KEY`, `KINESCOPE_PARENT_ID` |
| S3 | `STORAGE_DRIVER=s3`, `S3_ENDPOINT`, `S3_BUCKET`, `S3_ACCESS_KEY`, `S3_SECRET_KEY` |

Вместе с S3 worker выносится в отдельный сервис, и демо-вход можно
выключить (`DEMO_LOGIN_ENABLED=false`).
