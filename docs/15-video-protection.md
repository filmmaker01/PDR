# Защита видео: целевая архитектура и план работ

Документ описывает, как перевести видеомодуль на максимально закрытый просмотр
внутри Telegram Mini App, что для этого меняется в коде, и какие ограничения
платформы выяснены по документации, а какие нужно проверить на устройствах.

Код по этому документу ещё не менялся.

Оговорка по постановке: Supabase Storage в проекте не используется и никогда не
использовался — видео с самого начала лежат у видеопровайдера, а не в нашем
файловом хранилище. Отдельно «убирать Supabase» нечего.

## 1. Что есть сейчас

| Файл | Что делает |
|---|---|
| `apps/api/src/infra/video/video.types.ts` | контракт провайдера: `PlaybackTicket` с `embedUrl` **и `hlsUrl`** |
| `apps/api/src/infra/video/kinescope-video.provider.ts` | создаёт видео с `privacy_type: 'nobody'`, отдаёт TUS-адрес загрузки, при выдаче билета возвращает `embed_link` и `hls_link` |
| `apps/api/src/modules/learning/catalog/video.service.ts` | запись `VideoAsset`, опрос статуса, `issuePlayback` |
| `apps/api/src/modules/learning/student/learning.service.ts:203` | выдаёт билет вместе с уроком, если этап открыт и доступ активен |
| `apps/miniapp/src/features/learning/VideoPlayer.tsx` | **при наличии `hlsUrl` играет через `<video controls>`**, иначе iframe |
| `apps/admin/src/features/course/VideosPage.tsx` | создаёт запись и показывает адрес загрузки для копирования |

Что из требований уже выполнено: приватность видео у провайдера, серверная
проверка доступа перед выдачей билета, TTL билета (`VIDEO_PLAYBACK_TTL_SEC`),
отдельной кнопки скачивания нет.

Что нарушено или отсутствует:

1. **`hlsUrl` отдаётся клиенту.** Это прямая ссылка на поток: её видно в
   DevTools и в логах сети, её можно скормить `ffmpeg`/`yt-dlp`. Требование
   «отсутствие прямых публичных URL» этим нарушено.
2. **`<video controls>`** даёт нативное меню браузера с пунктом «Скачать» и
   Picture-in-Picture.
3. Нет DRM, нет водяного знака, нет ограничения по домену.
4. Токен просмотра одноразовым не является: выданная ссылка живёт до
   истечения TTL и не отзывается при окончании курса.
5. Загрузка из админки не реализована: преподаватель получает адрес и должен
   загружать файл сторонним TUS-клиентом.

## 2. Целевая архитектура

Пять рубежей, каждый работает самостоятельно; если верхний недоступен на
платформе, нижние остаются.

```
1. Хранение     Kinescope, privacy=nobody, DRM-шифрование, whitelist домена
2. Допуск       наш сервер: этап открыт + доступ активен + сессия не отозвана
3. Сессия       drmauthtoken (JWT, TTL 2–5 мин) + запись VideoViewSession
4. Проверка     Kinescope дергает наш auth backend → 200/403 на каждую лицензию
5. Следы        динамический watermark с идентификатором ученика
```

### 2.1 Выдача просмотра

```
Mini App                     Наш API                      Kinescope
   │ GET .../lessons/:key       │                              │
   ├───────────────────────────►│ проверка: этап открыт,       │
   │                            │ доступ к курсу активен       │
   │                            ├── создаёт VideoViewSession   │
   │                            ├── подписывает drmauthtoken   │
   │◄── embedUrl (без hlsUrl) ──┤   (sub=sessionId, TTL 5 мин) │
   │                                                           │
   │ iframe player.kinescope.io/<id>?drmauthtoken=…&watermark=…│
   ├──────────────────────────────────────────────────────────►│
   │                            │◄─ POST /v1/video/authorize ──┤
   │                            │   (проверка токена + прав)   │
   │                            ├── 200 / 403 ────────────────►│
   │◄─────────── воспроизведение с лицензией ──────────────────┤
```

Ключевое отличие от текущей схемы: клиенту не выдаётся ничего, что можно
воспроизвести без участия нашего сервера. Даже валидный `embedUrl`
бесполезен после отзыва сессии — Kinescope спросит разрешение у нас.

### 2.2 Водяной знак

Kinescope умеет динамический водяной знак: в embed-код передаётся параметр
`watermark` со значением, которое подставляет наш сервер; надпись появляется в
случайных местах экрана и не исчезает на паузе и перемотке. Это ровно то
поведение, которое требуется.

Содержимое метки: не телефон и не имя, а короткий идентификатор, по которому мы
сами найдём ученика, например `PDR·{enrollmentShortId}·{ddMM-HHmm}`. Так утечка
самой метки не раскрывает персональные данные, а источник слива определяется по
нашей базе.

### 2.3 Отзыв доступа

`VideoViewSession` помечается отозванной, когда:

- закончился или отозван доступ к продукту `course` (`access.expire`,
  админское снятие доступа);
- ученик отчислен из группы;
- открыта новая сессия на тот же урок с другого устройства (одна активная
  сессия на урок);
- прошло время жизни сессии.

Отозванная сессия перестаёт получать 200 от нашего auth backend, и следующий
запрос ключа проваливается. Насколько быстро это прервёт уже идущий просмотр,
зависит от интервала ротации ключей у Kinescope — **это надо уточнить у них**
(ожидание: перезапрос при смене периода, не мгновенно).

## 3. Совместимость DRM с Telegram WebView

Это главный риск всей схемы, поэтому здесь только проверяемые факты и явно
помеченные пробелы.

| Платформа | Движок | Что известно | Вывод |
|---|---|---|---|
| **Telegram Android** | Android System WebView | В клиенте Telegram обработчик `onPermissionRequest` покрывает только `RESOURCE_AUDIO_CAPTURE` и `RESOURCE_VIDEO_CAPTURE`; ветки `RESOURCE_PROTECTED_MEDIA_ID` нет, `default` тоже нет. Без выдачи этого разрешения EME не может запросить лицензию. | **DRM не заработает** |
| **Telegram iOS** | WKWebView | Widevine на Apple-платформах не поддерживается в принципе; FairPlay в Safari работает, но для WKWebView разработчики сообщали об отсутствии `window.WebKitMediaKeys`, официального подтверждения поддержки нет. На iOS 17/18 есть открытые баги FairPlay. | **Скорее всего не заработает, нужна проверка** |
| **Telegram Desktop, Windows** | Edge WebView2 | Widevine в WebView2 не входит: открытый feature request в трекере WebView2. PlayReady поддерживается, но Kinescope его не заявляет. | **DRM не заработает** |
| **Telegram Desktop, macOS** | WKWebView | То же, что iOS. | **Нужна проверка** |
| **Telegram Desktop, Linux** | WebKitGTK | Widevine в сборках WebKitGTK по умолчанию нет. | **DRM не заработает** |
| **Telegram Web** | обычный Chrome/Safari | Штатная поддержка Widevine/FairPlay. | **Работает** |

Вывод, который надо принять до написания кода: **DRM нельзя класть в
фундамент схемы.** Внутри Telegram Mini App он в лучшем случае доступен части
пользователей. Архитектура должна работать без него и включать его как
дополнительный слой там, где платформа позволяет.

Проверять это предположениями нельзя — ниже протокол проверки на живых
устройствах (раздел 6). До его прохождения считаем, что DRM в Telegram WebView
не работает нигде, кроме Telegram Web.

## 4. Fallback: самое защищённое без DRM

Если проверка подтвердит, что DRM в WebView недоступен, схема остаётся той же,
кроме слоя шифрования. Все остальные требования выполняются полностью:

| Требование | Как выполняется без DRM |
|---|---|
| Нет прямых публичных URL и MP4 | `hlsUrl` не отдаётся вообще; только iframe плеера; у видео `privacy_type: nobody` |
| Нет скачивания | нативный `<video>` не используется, значит нет меню браузера; в плеере отключаются загрузка и PiP |
| Просмотр после серверной проверки | без изменений: билет выдаётся только при открытом этапе и активном доступе |
| Короткоживущие токены | `drmauthtoken` с TTL 2–5 минут + запись сессии |
| Ограничение по origin | whitelist домена в настройках Kinescope: встраивание только с нашего домена |
| Отзыв после окончания курса | отзыв сессии + снятие доступа; повторная выдача билета невозможна |
| Динамический watermark | работает независимо от DRM |

Чего не будет без DRM: шифрования сегментов ключом устройства и блокировки
записи экрана на уровне ОС. То есть от «технически подкованный человек снимет
экран» защищает только водяной знак — но он как раз для этого и нужен:
поймать источник, а не сделать съёмку невозможной.

Промежуточный вариант, который стоит запросить у Kinescope: работает ли
внешняя авторизация и HLS-шифрование **без** включённого DRM. В публичной
документации внешняя авторизация описана в связке с DRM; если она доступна и
отдельно, fallback становится заметно сильнее. **Вопрос в список к поддержке.**

## 5. Что меняется в коде

### 5.1 Контракт провайдера

`apps/api/src/infra/video/video.types.ts`

- убрать `hlsUrl` из `PlaybackTicket` — это и есть та самая прямая ссылка;
- `issuePlayback` принимает не только `userId`, но и контекст: `sessionId`,
  `watermark`, `lessonKey`;
- добавить `revokeSession` в интерфейс — провайдер может не уметь, тогда
  no-op, а отзыв живёт на нашей стороне.

### 5.2 Kinescope-провайдер

`kinescope-video.provider.ts`

- `issuePlayback` перестаёт запрашивать `hls_link` и собирает embed-URL сам:
  `https://kinescope.io/embed/<id>?drmauthtoken=<jwt>&watermark=<mark>`;
- при создании видео задавать шаблон плеера с включёнными watermark и
  запретом скачивания;
- `createUpload` возвращает данные для загрузки из браузера (см. 5.6).

### 5.3 Новый модуль доступа к видео

`apps/api/src/modules/learning/video-access/`

- `video-session.service.ts` — выпуск и отзыв сессий, подпись JWT отдельным
  секретом (`VIDEO_TOKEN_SECRET`, не тот же, что у пользовательских сессий);
- `video-authorize.controller.ts` — **публичный** эндпоинт
  `POST /v1/video/authorize`, который дергает Kinescope: проверяет подпись
  токена, живость сессии, повторно проверяет открытость этапа и доступ,
  отвечает 200 или 403. Обязательно: rate limit, подпись запроса от Kinescope
  (уточнить, как они её делают), запись каждой проверки в аудит;
- при выдаче — отзыв предыдущих активных сессий того же ученика на тот же урок.

### 5.4 Схема базы

Новая модель:

```prisma
model VideoViewSession {
  id            String    @id @default(uuid()) @db.Uuid
  userId        String    @map("user_id") @db.Uuid
  enrollmentId  String    @map("enrollment_id") @db.Uuid
  lessonId      String    @map("lesson_id") @db.Uuid
  videoAssetId  String    @map("video_asset_id") @db.Uuid
  watermark     String
  issuedAt      DateTime  @default(now()) @map("issued_at") @db.Timestamptz(6)
  expiresAt     DateTime  @map("expires_at") @db.Timestamptz(6)
  revokedAt     DateTime? @map("revoked_at") @db.Timestamptz(6)
  revokedReason String?   @map("revoked_reason")
  lastCheckAt   DateTime? @map("last_check_at") @db.Timestamptz(6)
  checkCount    Int       @default(0) @map("check_count")
  ip            String?
  userAgent     String?   @map("user_agent")
}
```

Частичный уникальный индекс «одна активная сессия на ученика и урок» —
по образцу уже имеющихся `submission_single_active` и `attempt_single_active`.

Плюс поля в `VideoAsset`: `drmEnabled`, `watermarkEnabled` — чтобы включать
защиту выборочно и уметь откатиться на конкретном видео.

### 5.5 Плеер в Mini App

`apps/miniapp/src/features/learning/VideoPlayer.tsx`

- удалить ветку с `<video>` целиком: остаётся только iframe;
- **прогресс просмотра переезжает на IFrame Player API Kinescope**
  (`postMessage`-события времени) вместо `timeupdate` у `<video>`. Это
  единственное место, где меняется поведение продукта, и его надо проверить
  отдельно: на нём держится порог `minWatchPercent` и отметка «урок пройден»;
- при истечении билета (`expiresAt`) — перезапрос билета без перезагрузки
  страницы;
- запрет контекстного меню и перетаскивания поверх контейнера плеера.

### 5.6 Загрузка из админки

`apps/admin/src/features/course/VideosPage.tsx`

Сейчас преподаватель копирует адрес и грузит файл чем-то ещё. Нужна загрузка
прямо в браузере: `tus-js-client`, выбор файла, прогресс, докачка при обрыве.
Токен Kinescope в браузер отдавать нельзя, поэтому:

- наш сервер создаёт видео и выдаёт **одноразовый** upload-URL с коротким TTL;
- если Kinescope требует Bearer-токен при загрузке, загрузка идёт через наш
  API как прокси-стрим (`PUT /v1/admin/videos/:id/content`), а не напрямую.
  **Какой из двух вариантов возможен — уточнить в документации TUS Kinescope.**

### 5.7 Отзыв доступа

- `apps/api/src/modules/access/jobs/access-expire.handler.ts` — при истечении
  доступа отзывать активные видеосессии пользователя;
- `admin-access.controller.ts` — то же при ручном отзыве и приостановке;
- отчисление из группы — там же.

### 5.8 Конфигурация

Новые переменные (в `.env.example`, с проверками в `env.schema.ts`):

```
VIDEO_DRM_ENABLED=false          # включается после проверки на устройствах
VIDEO_TOKEN_SECRET=              # подпись drmauthtoken, отдельный секрет
VIDEO_SESSION_TTL_SEC=300        # жизнь сессии просмотра
VIDEO_WATERMARK_ENABLED=true
KINESCOPE_AUTH_CALLBACK_SECRET=  # проверка запросов от Kinescope к нам
KINESCOPE_PLAYER_TEMPLATE_ID=    # шаблон плеера с watermark и без скачивания
```

Проверка конфигурации: при `APP_ENV=production` и `VIDEO_PROVIDER=kinescope`
пустой `VIDEO_TOKEN_SECRET` не должен пропускаться.

## 6. Что проверить на устройствах до написания кода

Это надо сделать руками, на аккаунте Kinescope, до начала работ — иначе
половина плана может оказаться нерабочей.

1. Создать в Kinescope тестовое видео, включить DRM, включить динамический
   водяной знак, ограничить домен адресом staging.
2. Встроить его на страницу урока staging Mini App.
3. Открыть Mini App и записать результат по каждой платформе:

| Платформа | Играет? | Водяной знак? | Ошибка в консоли |
|---|---|---|---|
| Telegram iOS (iPhone) | | | |
| Telegram Android | | | |
| Telegram Desktop Windows | | | |
| Telegram Desktop macOS | | | |
| Telegram Web (Chrome) | | | |

4. Повторить с выключенным DRM (остальное включено) — это проверка fallback.

Что смотреть в ошибках: `NotSupportedError`, `requestMediaKeySystemAccess`,
`MEDIA_ERR_SRC_NOT_SUPPORTED`, отсутствие `window.WebKitMediaKeys` на iOS,
молчаливое зависание на Android (признак неотвеченного запроса разрешения).

Отладка на устройстве: на Android — `chrome://inspect` с подключённым
телефоном, на iOS — Web Inspector в Safari на Маке.

## 7. Вопросы к поддержке Kinescope

1. Работает ли внешняя авторизация (auth backend) **без** включённого DRM?
2. Как подписываются запросы Kinescope к нашему auth backend — как проверить,
   что запрос действительно от них?
3. С какой периодичностью плеер перезапрашивает разрешение во время просмотра?
   От этого зависит, через сколько отзыв доступа реально прервёт просмотр.
4. Поддерживается ли в тарифе PlayReady — это единственный DRM, доступный в
   WebView2 на Telegram Desktop для Windows.
5. Формат параметра `watermark`: ограничения по длине и допустимым символам,
   можно ли управлять частотой смены положения.
6. Загрузка TUS: можно ли выдать одноразовый upload-URL, который не требует
   основного Bearer-токена в браузере.
7. Есть ли у плеера параметры, запрещающие скачивание и Picture-in-Picture.

## 8. Порядок работ

| Этап | Содержание | Зависит от |
|---|---|---|
| V0 | Проверка на устройствах (раздел 6), ответы поддержки (раздел 7) | аккаунт Kinescope |
| V1 | Убрать `hlsUrl` и `<video>`, перевести прогресс на IFrame Player API | — |
| V2 | `VideoViewSession`, выпуск и отзыв, auth backend, аудит | V1 |
| V3 | Динамический watermark, whitelist домена, шаблон плеера | V1 |
| V4 | Загрузка из админки через TUS | ответ по п. 6 раздела 7 |
| V5 | DRM включается там, где подтверждена работа (флаг на видео) | V0, V2 |

V1 полезен сам по себе и не зависит от ответов Kinescope: он закрывает самую
серьёзную из текущих дыр — прямую ссылку на поток.
