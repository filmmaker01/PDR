# 11. Тестирование, безопасность, готовность к пилоту

## Уровни тестов

| Уровень | Инструмент | Что покрывает | Когда запускается |
|---------|-----------|---------------|-------------------|
| Unit | Vitest | чистая логика: проверка initData/Login Widget, `StageAccessService`, расчёт сметы и скидок, `OrderStateMachine`, статус оплаты, автопроверка тестов, парсинг телефонов/номеров, деньги/даты/tz, permissions | на каждый коммит |
| Integration (API) | Vitest + Supertest, реальная PostgreSQL в Docker (testcontainers), MinIO в Docker, Telegram API — mock-сервер | каждый эндпоинт: успешный путь, валидация, права, изоляция, идемпотентность, транзакционность | на каждый коммит |
| Contract | OpenAPI snapshot | несовместимые изменения API ломают сборку клиента | на каждый коммит |
| E2E | Playwright (Chromium + WebKit) | сценарии F1–F10 из `07-user-flows.md` на Mini App (эмуляция Telegram: подменяется `window.Telegram.WebApp` с валидным `initData`, подписанным тестовым токеном) и на админке (тестовый вход через `/auth/test-login`, доступен только при `APP_ENV=test`) | на PR в main и перед деплоем |
| Security | Vitest, генерируемые тесты | см. ниже | на каждый коммит |
| Ручное на устройствах | чеклист | Telegram iOS, Android, Desktop (macOS/Windows), веб-версия Telegram | перед релизом |

Целевое покрытие: логика прав/доступов/денег/state machine — 100% веток; остальное — по факту сценариев, без погони за процентом.

## Обязательные security-тесты

Генерируются из реестра маршрутов, чтобы новый эндпоинт без теста не прошёл CI:

1. **Изоляция мастерских**: для каждого маршрута `/workspaces/:id/**` — пользователь мастерской A с валидным объектом мастерской B в пути/теле → 404; участник, деактивированный в A → 404; пользователь без CRM-гранта → 403 на запись, 200 на чтение.
2. **Закрытый этап**: урок/видео/материалы/сдача/попытка закрытого этапа → 403 `stage_locked` с причинами; с override `unlock` → 200; с истёкшим грантом → 403 `product_access_required`.
3. **Сессии**: отозванная сессия → 401 на следующем запросе; бан → 401; повторное использование старого refresh-токена → отзыв всех сессий.
4. **initData**: неверная подпись, изменённое поле, просроченный `auth_date`, отсутствующий `hash` → 401; корректный → 200. Аналогично для Login Widget.
5. **Файлы**: presign на чужой `workspaceId` → 404; `GET /files/:id/url` на файл чужой сдачи/заказа → 404; superset mime → 422; превышение размера → 422; `complete` с несовпадающим размером → 422.
6. **Идемпотентность**: два одинаковых `POST` с одним ключом → один объект и одинаковый ответ; тот же ключ с другим телом → 422.
7. **State machine**: все запрещённые переходы → 409; сотрудник на чужом заказе → 404.
8. **Календарь**: пересечение → 409 с конфликтами; `allow_overlap` сотрудником → 403; владельцем → 201.
9. **Оплаты**: `UPDATE/DELETE` невозможны (нет маршрутов; роль БД без прав) — тест через прямой SQL от роли приложения ожидает ошибку.
10. **Админ и CRM**: админ платформы на любом `/workspaces/:id/**` без членства → 404.
11. **Webhook**: неверный secret в пути или заголовке → 403; повторная доставка того же `update_id` → обрабатывается один раз (таблица/кеш обработанных `update_id` на 24 часа).
12. **Инъекции/массовое присваивание**: DTO со строгими zod-схемами (`strict()`), неизвестные поля → 422; `workspace_id`, `created_by`, `paid_minor` из тела игнорируются.

## Тесты обучения (критичные)

- `StageAccessService`: таблица случаев (режим × дата × предыдущий этап × override × грант) → ожидаемый статус и набор причин.
- Публикация версии: валидация (уроки без видео, тест без правильных ответов, дубли ключей) → отчёт ошибок; успешная публикация создаёт новый черновик.
- Перенос группы на версию: прогресс по совпадающим ключам сохранён; новый обязательный урок «закрывает» этап обратно — отчёт dry-run это показывает.
- Экзамен: лимит попыток, cooldown, дедлайн → `expired` с автопроверкой; ответы не содержат `is_correct` до завершения.
- Сдача: нельзя две активные; `returned` → новая попытка с `attempt_no+1`; `claim` истекает через 30 минут.

## Тесты CRM (критичные)

- Создание заказа одной транзакцией с новым клиентом/авто/записью; ошибка на записи (пересечение) откатывает всё.
- Смета: расчёт итогов с округлением на граничных значениях; согласование делает старую `superseded`; изменение прайса не меняет позиции; редактирование `agreed` → 409.
- Оплаты: `paid_minor` и `payment_status` после последовательности оплата → возврат → корректировка; предоплата без сметы; выдача с долгом → появляется в `/debts`.
- Аналитика: фиксированный набор данных → ожидаемые числа; границы периода в часовом поясе мастерской (запись в 23:30 по Москве попадает в «сегодня»).
- Анонимизация клиента: ПДн стёрты, заказы и оплаты и суммы на месте, аудит записан.

## Тесты Telegram/клуба/уведомлений

- Mock Telegram API: `sendMessage` 200/403/429; `approveChatJoinRequest`; `banChatMember`.
- join request без гранта → decline + событие; с грантом → approve + `member`.
- Отзыв гранта → задача `club.remove` → статус `removed`; 429 → повтор; 400 «user not found» → статус синхронизирован.
- Уведомление не отправлено (403) → бизнес-операция завершена, статус `skipped`, `is_bot_blocked=true`.
- Напоминание о записи: перенос записи → старое `skipped`, новое запланировано; дедупликация по `dedupe_key`.

## Качество кода и CI

- ESLint (typescript-eslint, import/no-cycle, правило запрета прямых Prisma CRM-моделей вне репозиториев), Prettier, `tsc --noEmit` для всех пакетов.
- CI (`.github/workflows/ci.yml`): install → lint → typecheck → unit → integration (services: postgres, minio) → build → e2e (на PR в main). Артефакты: отчёт Playwright, покрытие.
- `deploy-staging.yml`: на merge в `main` — сборка образов, push в registry, миграции, выкат на staging, smoke-тест (`/health/ready`, вход тестового пользователя).
- `deploy-prod.yml`: по тегу `v*` с ручным подтверждением (GitHub Environment), pre-deploy backup, миграции, выкат, smoke.
- Зависимости: Renovate/Dependabot еженедельно; `pnpm audit` в CI (fail на high в production-зависимостях).

## Безопасность приложения

- Все секреты в env; `SESSION_JWT_SECRET` и `TELEGRAM_WEBHOOK_SECRET` ротируются скриптом (`infra/scripts/rotate-keys`).
- Заголовки: `helmet`, CORS только для доменов Mini App и админки, CSP на фронтах (`frame-ancestors` для Telegram WebView: `https://web.telegram.org` и `tg:`), `X-Frame-Options` не ставится (ломает WebView).
- Rate limiting: `/auth/*` — по IP и по Telegram ID; общий — по сессии; webhook — по секрету.
- Логи не содержат `initData`, токенов, телефонов клиентов (маскирование в pino).
- Роль БД для API: без `UPDATE/DELETE` на `payment_entries`, `audit_log`, `order_status_history`, `reviews`; миграции — отдельной ролью.
- Presigned URL: короткий TTL, `Content-Type` и `Content-Length` зафиксированы в подписи загрузки.
- Обработка файлов в worker'е с ограничением памяти/времени (sharp, ffprobe с таймаутом), без выполнения содержимого.
- Ошибки не раскрывают stack trace в production; `requestId` для поддержки.

## Чеклист перед пилотом

- [ ] Пользователь мастерской A не получает заказы, клиентов, фото мастерской B ни по ID, ни по ссылке на файл (автотесты зелёные + ручная проверка на staging).
- [ ] Закрытый этап недоступен через прямой запрос к API (видео, материалы, сдача, экзамен).
- [ ] Отзыв доступа и бан действуют на существующие сессии в течение ≤ 5 секунд.
- [ ] Повторный запрос не создаёт дубль заказа, оплаты, сдачи, попытки экзамена.
- [ ] Прерванная загрузка фото (потеря сети на 30 с, сворачивание приложения) восстанавливается или повторяется без потери уже загруженных файлов.
- [ ] Даты и календарь корректны в часовом поясе мастерской (проверить мастерскую в UTC+7 при сервере в UTC).
- [ ] Mini App работает в Telegram iOS, Android, Desktop, Web: вход, видео, камера, загрузка, share приглашения, MainButton.
- [ ] Резервная копия восстанавливается на staging по `restore.sh`; проверен объём и время восстановления.
- [ ] Worker после принудительного kill доводит незавершённые задачи; очередь видна в админке.
- [ ] Уведомления доходят; заблокировавший бота пользователь не ломает очередь.
- [ ] Клуб: заявка без доступа отклоняется, с доступом одобряется, отзыв удаляет, продление позволяет вернуться.
- [ ] Экспорт CRM открывается в Excel (UTF-8 BOM, разделитель `;`), суммы в рублях с копейками.
- [ ] Sentry получает ошибки с `requestId`; логи без ПДн.
- [ ] Нагрузочная проверка: 50 одновременных загрузок фото и 200 RPS на чтение списков не деградируют API (k6, staging).
- [ ] Документация для администратора и владельца: как выдать доступ, как пригласить сотрудника, как восстановить данные.

## Реализация проверок (этап 16)

- Обязательные проверки безопасности из списка выше собраны в `apps/api/test/security.spec.ts`: маршруты закрыты по умолчанию (нет сессии → 401), изоляция мастерских, администратор платформы без членства, истёкший доступ (чтение да, запись нет), строгие схемы и игнорирование служебных полей, конфликт ключа идемпотентности, отсутствие маршрутов правки оплат, отзыв сессии и бан, секрет вебхука, ограничения файлов.
- Сценарии F1–F10 проходят целиком в `apps/api/test/e2e-flows.spec.ts` на уровне API — тем же путём, которым их проходит интерфейс. Браузерный прогон Playwright сознательно не добавлен: он проверяет клиент Telegram и вёрстку, а это и так требует ручной проверки на реальных устройствах перед пилотом (см. `docs/manual/pilot-checklist.md`).
- Нагрузочный сценарий: `infra/load/read-load.js` (k6, до 200 запросов в секунду на чтение списков, пороги по доле ошибок и времени ответа). Загрузка фотографий отдельным скриптом не нагружается: файлы идут напрямую в хранилище, минуя API.
- Демонстрационные данные защищены от попадания в production: `prisma/seed.ts` отказывается работать при `APP_ENV=production` и `SEED_DEMO=true`.
