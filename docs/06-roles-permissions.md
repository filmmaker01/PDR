# 06. Роли, права, изоляция

## Три независимых измерения «кто я»

| Измерение | Где хранится | Значения |
|-----------|--------------|----------|
| Роль платформы | `platform_roles` | `admin`, `curator` (может быть обе) |
| Ученик | `enrollments` (+ действующий `access_grants.course`) | зачисление в конкретную группу |
| Участник мастерской | `workspace_members` (+ действующий `access_grants.crm` у мастерской) | `owner`, `employee`; пользователь может состоять в нескольких мастерских |

Один человек может одновременно быть учеником, владельцем одной мастерской и сотрудником другой. `GET /me` возвращает все контексты; клиент выбирает активную мастерскую (сохраняется в `localStorage`, проверяется сервером при каждом запросе).

## Матрица прав

Обозначения: ✓ — полностью, ◐ — с ограничением (описано ниже), — нет.

Администратор платформы **не имеет доступа к данным CRM** ни через API, ни через админку. Поддержка мастеров выполняется по их запросу: владелец может добавить сотрудника поддержки сам (приглашение), и это будет видно в его журнале.

## Реализация

`packages/shared/permissions.ts`:

```ts
export const WORKSPACE_PERMISSIONS = {
  owner: ['workspace.manage', 'members.manage', 'clients.*', 'orders.*', 'appointments.*',
          'estimates.*', 'payments.*', 'price_list.*', 'analytics.read', 'audit.read', 'export.run'],
  employee: ['clients.read', 'clients.write', 'orders.read_own', 'orders.create', 'orders.write_own',
             'appointments.read', 'appointments.write_own', 'price_list.read',
             'estimates.write_own?employees_can_edit_estimates', 'payments.write_own?employees_can_take_payments',
             'orders.read_all?employees_see_all_orders', 'orders.assign?employees_can_assign'],
} as const;
```

Суффикс `?setting` означает, что право активно только при включённой настройке мастерской. Guard `@Can('orders.write_own')` проверяет наличие права у роли с учётом настроек; политика в сервисе проверяет «own» (`order.assignee_member_id === ctx.member.id || order.created_by === ctx.userId`).

Для обучения права проверяются через контекст зачисления (`enrollment.user_id === user.id`) и кураторства (`cohort_curators`).

## Изоляция мастерских — обязательные меры

1. `workspace_id` в каждой CRM-таблице, составные FK (см. `03-database.md`).
2. Guard `@Workspace()` резолвит членство по `(workspaceId, userId, is_active=true)`; отсутствие → 404.
3. Репозитории CRM принимают `workspaceId` обязательным параметром; lint запрещает прямое использование Prisma-моделей CRM вне репозиториев.
4. Ссылки на файлы выдаются только после проверки привязки файла к сущности мастерской.
5. Поиск (`?q=`) выполняется внутри `workspace_id`; полнотекстовые индексы включают `workspace_id`.
6. Идентификаторы — UUID v4 (неперечислимые), но это не защита, а гигиена.
7. Интеграционные тесты изоляции: для каждого CRM-эндпоинта есть тест «пользователь мастерской A обращается к объекту мастерской B по ID → 404» (генерируется из списка маршрутов, см. `11-testing-quality.md`).
8. Аудит платформы не содержит `before/after` CRM-сущностей.

## Продуктовые доступы и их следствия

| Событие | Курс | CRM | Клуб |
|---------|------|-----|------|
| Выдан | зачисление активно; этапы по правилам | раздел «Мастерская» полностью | кнопка «Вступить» активна |
| Истёк / отозван | раздел «Обучение» показывает «Доступ истёк» с прогрессом; видео/сдачи/экзамены недоступны через API | данные только на чтение + экспорт; создание/изменение → 403 `product_access_required` | ссылка недоступна; worker удаляет из группы |
| Приостановлен (`suspended`) | как истёк, но с другой формулировкой | как истёк | как истёк |
| Продлён / возобновлён | всё возвращается, прогресс сохранён | запись снова доступна | можно подать заявку снова |

## Реализация (этап 2)

- `packages/shared/permissions.ts` — единственное описание прав. Роль плюс настройки мастерской дают набор разрешений; условные права (`?setting`) включаются переключателями владельца. Покрыто тестом «сотрудник не получает права владельца ни при каких настройках».
- `WorkspaceGuard` собирает контекст мастерской по `:workspaceId`: членство, активность участника, настройки, набор прав, состояние доступа к CRM. Отсутствие членства, неактивный участник, чужой или несуществующий идентификатор — везде **404**.
- Отсутствие нужного права тоже даёт 404, а не 403: сотрудник не должен узнавать о существовании разделов владельца.
- При истёкшем доступе к CRM разрешены `GET`/`HEAD` и маршруты, помеченные `@AllowExpiredAccess()` (выгрузка); любая запись отвечает `403 product_access_required`. Проверка идёт по датам гранта, а не по статусу в базе, поэтому отзыв действует немедленно, не дожидаясь фоновой задачи.
- Изоляция закреплена на трёх уровнях: guard, репозиторный слой `WorkspaceScopedRepository` с обязательным `workspaceId` и правило ESLint, запрещающее обращаться к Prisma-моделям CRM вне репозиториев.
- База проверяет инварианты сама: частичный уникальный индекс «один активный владелец», согласованность субъекта гранта, обязательный курс для доступа к курсу, корректный диапазон дат, соответствие продукта типу субъекта.
- Приглашение хранится как sha256 токена; ссылка с токеном показывается один раз. Принять можно однократно, при ограничении по номеру телефон сверяется после нормализации.
- Передача владения выполняется одной транзакцией с понижением текущего владельца первым — иначе частичный уникальный индекс отклонит операцию.
