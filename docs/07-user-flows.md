# 07. Пользовательские сценарии

Каждый сценарий описан по шагам с указанием эндпоинтов и обработкой ошибок. Сценарии из этого файла — основа для e2e-тестов.

---

## F1. Первый вход в Mini App

1. Пользователь открывает бота → кнопка меню «Открыть приложение» (или `t.me/<bot>/app`). Mini App загружается.
2. Клиент читает `initData`, вызывает `POST /auth/telegram/miniapp`.
3. Сервер валидирует подпись и `auth_date`, создаёт/обновляет `users`, выдаёт сессию.
4. Клиент вызывает `GET /me`. По содержимому:
   - есть зачисления **и** мастерские → главный экран с тремя вкладками, активна последняя использованная;
   - только зачисления → вкладка «Обучение»; вкладка «Мастерская» показывает экран «У вас пока нет мастерской» с объяснением, как получить доступ;
   - только мастерская → «Мастерская»;
   - ничего → экран-приветствие с описанием продуктов и контактом для покупки; `startAction` (приглашение) обрабатывается до этого.
5. Если `user.bot_write_allowed=false`, показывается ненавязчивый баннер «Разрешить уведомления» → `WebApp.requestWriteAccess()` → при согласии `POST /me/bot-write-allowed`.

Ошибки: недействительный `initData` → экран «Откройте приложение из Telegram»; сессия истекла → прозрачный refresh; refresh невалиден → повторный вход через initData без участия пользователя (initData доступен всё время работы Mini App).

## F2. Ученик проходит этап

1. «Обучение» → «Мой курс» (`GET /learning/enrollments/:id`): карта трёх этапов, у каждого статус и причина блокировки (`Откроется 15 ноября`, `Практика ещё не принята`, `Нужно пересдать экзамен`).
2. Открытый этап → список уроков с галочками, заданий с состоянием последней сдачи, экзаменов с попытками.
3. Урок (`GET .../lessons/:key`): плеер с `playbackUrl`, восстанавливается `watch_position_sec`; каждые 10 с и при паузе/уходе — `PUT .../progress`. Материалы — по подписанным ссылкам.
4. Кнопка «Урок пройден» → `POST .../complete`. Если `min_watch_percent` не достигнут → 422 с сообщением «Посмотрите не менее 80% урока».
5. Задание → «Сдать работу»: создаётся черновик, пользователь выбирает фото/видео (камера или галерея), каждое грузится через presign напрямую в S3 с прогресс-баром и повтором при ошибке; после `complete` файл привязывается к сдаче. Текст описания. «Отправить» → `submit` (Idempotency-Key). Экран «Работа отправлена, куратор проверит».
6. Куратор возвращает работу → уведомление в боте «Работа по заданию «…» возвращена на доработку: <комментарий>» с кнопкой открытия Mini App на этой сдаче. Ученик видит комментарий и историю, создаёт новую сдачу (attempt 2) — предыдущие файлы можно скопировать в новую.
7. Принято → уведомление, галочка у задания.
8. Тест: экран правил (вопросов, порог, лимит времени, попыток осталось) → «Начать» → вопросы по одному или списком, таймер, ответы сохраняются сразу → «Завершить» → результат с процентом, `passed`, разбор (правильные ответы и пояснения показываются по настройке экзамена `show_explanations`). Не сдал → «Пересдать можно через N часов», счётчик попыток.
9. Практический экзамен: как сдача задания + ожидание оценки куратора.
10. Когда все обязательные элементы выполнены → `stage_completions`; если следующий этап открыт по дате → уведомление «Открыт этап 2», карта курса обновляется. Если по дате ещё рано → на карте «Этап 2 откроется 15 ноября» (всё остальное выполнено).

Граничные случаи: обрыв связи при загрузке фото (повтор той же части, presign переиспользуется до `expiresAt`); истечение доступа посреди этапа (видео перестаёт выдаваться, прогресс сохранён, экран «Доступ истёк»); смена версии курса группой (ученик видит новые уроки без потери отметок).

## F3. Куратор проверяет работу

1. Куратор открывает админку (`admin.<domain>`), входит через Login Widget. Видит только разделы «Очередь проверок», «Мои группы», «Ученики».
2. Очередь (`GET /curator/review-queue`): сдачи по времени ожидания, фильтры. Открывает сдачу → `claim` (видно другим кураторам как «проверяет Иван»).
3. Просмотр фото/видео (подписанные ссылки, галерея с zoom), текста, истории предыдущих попыток и своих прошлых комментариев.
4. Решение: «Принять» или «Вернуть» с обязательным комментарием (по возможности — по критериям из `rubric`). `POST .../review`.
5. Ученик получает уведомление; сдача уходит из очереди; прогресс пересчитывается.
6. При необходимости уточнить — комментарий без решения (`review_comments`), сдача остаётся `in_review` за куратором.

Куратор работает и из Mini App (упрощённая очередь и проверка с телефона) — те же эндпоинты, экраны в разделе «Профиль → Кураторство».

## F4. Мастер оформляет заказ от записи до оплаты

1. «Мастерская» → «Сегодня»: в работе, готовы к выдаче, обращения (со счётчиками), записи на сегодня, активные заказы, кнопки «+ Обращение» и «+ Заказ».
2. Форма создания (`POST /orders` одной транзакцией): поиск клиента по телефону/имени (или «Новый клиент» — имя, телефон), автомобиль клиента или новый (марка, модель, номер), краткое описание, исполнитель (по умолчанию я), запись: дата, время, длительность, тип «Осмотр». Если слот занят → диалог с конфликтами; владелец может «Всё равно записать».
3. Клиент приезжает → карточка заказа → вкладка «Фото» → «Добавить «До»»: камера, несколько снимков, фон-загрузка с индикатором; при желании подпись «Капот» и привязка к позиции сметы позже.
4. Вкладка «Расчёт» → «Новая смета»: добавление позиций из прайса (тап по позиции подставляет цену) или вручную: элемент кузова, тип повреждения, размер, количество, материал, доступ, ребро, цена, комментарий; строки «Разборка/сборка» и «Доп. работы»; скидка % или сумма; итог обновляется с сервера. «Отправить клиенту» → `sent` (+ PDF/ссылка для мессенджера).
5. Клиент согласен → «Согласовать» → заказ `pending_approval → scheduled/in_progress`, согласованная сумма зафиксирована. Не согласен → «Отклонить» или «Новая версия» с изменёнными позициями.
6. Предоплата: вкладка «Оплаты» → «Добавить оплату»: сумма, способ, назначение «Предоплата», дата. Статус оплаты `partial`.
7. Ремонт: статус «В работе» (кнопка перехода), фото «В процессе». Готово → «Готов», фото «После».
8. Выдача: «Выдан» → если остаток > 0, диалог «Не оплачено N. Принять оплату сейчас?» → запись оплаты «Доплата». Остаток виден в карточке оплат заказа.
9. Позже клиент доплатил → запись «Доплата» → `paid`. Ошибка в сумме → «Корректировка» с указанием, какую запись исправляет, и комментарием.
10. Возврат клиенту → запись «Возврат».

Все действия видны в истории заказа и журнале мастерской.

## F5. Владелец приглашает сотрудника и назначает заказы

1. «Мастерская» → «Сотрудники» → «Пригласить»: роль «Сотрудник», необязательно телефон, срок ссылки. Получает deep-link `t.me/<bot>?startapp=inv_<token>` → «Поделиться» в Telegram.
2. Сотрудник открывает ссылку → Mini App → вход → `startAction` → экран «Вас приглашают в мастерскую «…» как сотрудника» → «Принять» (`POST /invitations/accept`). Если приглашение ограничено телефоном, а он не указан в профиле — запрос телефона через `requestContact`.
3. Владелец видит сотрудника в списке, задаёт цвет и отображаемое имя.
4. В заказе — «Исполнитель» → выбор сотрудника → сотрудник получает уведомление «Вам назначен заказ №…». В календаре — фильтр по исполнителям.
5. Деактивация сотрудника: «Деактивировать» → он теряет доступ к мастерской, его заказы остаются с ним как исполнителем в истории; владелец переназначает активные.

## F6. Администратор управляет доступами

1. Админка → «Доступы» → «Выдать»: выбор пользователя (поиск по username/телефону/Telegram ID; если пользователя ещё нет — «Создать ожидающего по Telegram ID» либо инструкция «попросите открыть бота»), продукт, срок, причина/номер оплаты.
   - Курс → одновременно выбирается группа → создаётся грант + зачисление.
   - CRM → выбирается мастерская или создаётся новая с владельцем.
   - Клуб → грант; пользователь видит кнопку «Вступить».
2. Продление: «Продлить до …» с причиной.
3. Отзыв: «Отозвать» с причиной → следствия немедленно (см. `06-roles-permissions.md`); для клуба — задача удаления; результат виден в карточке.
4. Дашборд показывает истекающие в ближайшие 7 дней доступы; уведомление пользователю за 7 и 1 день.

## F7. Вступление в клуб

1. Mini App → «Клуб» (кнопка рядом с курсом) → `GET /club`: если гранта нет — описание и контакт; если есть — «Вступить в клуб».
2. «Вступить» → `POST /club/join-link` → ссылка-приглашение с `creates_join_request=true` (одна общая ссылка группы, созданная ботом; не персональная).
3. Пользователь переходит, Telegram создаёт заявку → бот получает `chat_join_request` → задача `club.approve`: проверка `telegram_user_id → users → активный грант club`; да → `approveChatJoinRequest`, статус `member`; нет → `declineChatJoinRequest` + событие в журнал.
4. Отзыв/истечение → `club.remove`: `banChatMember` + `unbanChatMember` (пользователь исключён, может подать заявку позже), статус `removed`, уведомление «Доступ к клубу завершён».
5. Продление → пользователь снова видит «Вступить», заявка одобряется.
6. Ежедневная сверка: участники группы без гранта (например, добавленные админом вручную) — отчёт админу; удаление только по явному подтверждению в админке (чтобы не выкинуть преподавателей).

## F8. Вход администратора в веб-админку

1. `admin.<domain>/login` → кнопка Telegram Login Widget → Telegram возвращает подписанные данные → `POST /auth/telegram/widget`.
2. Сервер проверяет подпись и `auth_date`, находит пользователя, проверяет `platform_roles`; нет ролей → «Нет доступа к админке».
3. Резерв: «Войти через бота» → код + deep-link → подтверждение в боте → сессия.

## F9. Восстановление после ошибок и повторов

- Двойное нажатие «Оплата»/«Отправить работу»/«Начать тест» → второй запрос с тем же `Idempotency-Key` получает тот же ответ, дубля нет.
- Отправка уведомления не удалась (бот заблокирован) → операция (проверка, статус) завершена, уведомление `skipped`, пользователь увидит результат в приложении.
- Telegram 429 при массовой рассылке → очередь ждёт `retry_after`.
- Worker упал → задачи остаются в pg-boss, после рестарта выполняются; админ видит «worker недоступен» по heartbeat.

## F10. Экспорт и удаление данных

- Владелец: «Настройки → Экспорт данных» → выбор состава → задача → уведомление и ссылка (24 часа).
- Владелец: «Клиент → Удалить персональные данные» → подтверждение → анонимизация (заказы и деньги остаются, ФИО/телефон/заметки стираются, файлы фото заказов остаются, так как это документация ремонта; при желании — «Удалить фото заказов клиента» отдельным действием).
- Пользователь платформы: «Профиль → Удалить аккаунт» → заявка администратору (ручная процедура в 1.0: аккаунт банится, ПДн профиля анонимизируются, зачисления закрываются; данные мастерской, где он был сотрудником, остаются у мастерской).

## Реализация открытия этапов (этап 6)

Правило, утверждённое заказчиком, реализовано в `StageAccessService` буквально:

1. Ручное **закрытие** администратором перекрывает всё остальное.
2. Нет действующего доступа к курсу — закрыто, но прогресс сохранён и виден.
3. Обучение на паузе или прекращено — закрыто.
4. Ручное **открытие** администратором пропускает и срок, и требования предыдущего этапа.
5. Иначе проверяются **оба** условия сразу: наступил ли срок и завершён ли предыдущий этап. Нарушенные условия возвращаются **списком**, а не по одному: ученик видит и «Откроется 15 ноября», и «Практика ещё не принята» одновременно.

Срок считается по режиму группы: `interval` (по умолчанию) — дни от **личного** старта ученика (`enrollments.started_at`); `dates` — общие даты потока из `cohorts.stage_dates`. В обоих режимах требования предыдущего этапа действуют одинаково.

Прочее:

- Прогресс привязан к **ключам** (`lesson_key`, `assignment_key`, `exam_key`), поэтому перенос группы на новую версию курса его не теряет. Отчёт перед переносом показывает, у кого из учеников засчитанные этапы станут незавершёнными из-за новых обязательных элементов.
- Завершение этапов хранится материализованно (`stage_completions`) и пересчитывается после каждого события, которое на него влияет. Пересчёт умеет и **снимать** отметку, если требования выросли.
- Однократность уведомления об открытии этапа обеспечивает ключ дедупликации, а не сравнение «было/стало»: к моменту пересчёта изменение уже записано, поэтому сравнение состояний ненадёжно.
- Зачисление создаёт доступ к курсу и запись **одной транзакцией**: доступ без зачисления некуда применить, зачисление без доступа бессмысленно.
- Порог просмотра — вспомогательный показатель, но если он задан, отметить урок без него нельзя: иначе обязательность превращается в формальность. Процент просмотра только растёт, перемотка назад его не отнимает.

## F11. Обращение → оценка → запись → заказ (этап 17)

1. Клиент пишет в Telegram и присылает фото вмятины.
2. Мастер: «Мастерская» → «+ Обращение». Заполняет имя и телефон (или только ник),
   марку и модель, выбирает канал **Telegram** — источник проставляется сам как
   «онлайн».
3. «Добавить фото» → выбирает присланный снимок (или снимает с камеры, если
   клиент приехал).
4. На схеме автомобиля нажимает «Дверь» → карточка повреждения: тип
   «парковочная», размеры 4×4 см (класс `M` определяется сам), комментарий.
5. Создаёт обращение. Клиента в справочнике ещё нет — обращение живёт на
   свободном контакте.
6. Открывает снимок, обводит нужную вмятину и привязывает разметку к
   отмеченному повреждению. Оригинал остаётся нетронутым.
7. «Сделать оценку» → «По параметрам» → «Рассчитать по прайсу» → сумма из
   прайса. Округляет итог руками до удобной цифры и сохраняет. Обращение само
   переходит в «Оценено», сумма появляется в шапке.
8. Клиент думает. Мастер переводит обращение в «Перезвонить» и указывает дату —
   обращение попадает в список «Пора звонить» и в счётчик на главной.
9. Клиент согласился. «Записать в календарь» → дата, время, тип «Осмотр».
   В этот момент клиент и автомобиль заводятся в справочниках, обращение
   переходит в «Записан».
10. Клиент приехал. «Создать заказ» → повреждения, фотографии с разметкой и
    оценки переезжают в заказ; описание повреждений подставляется из
    комментария обращения. Мастер ничего не вводит заново.
11. Дальше — обычный поток заказа: смета из оценки, работа, оплата, выдача.

**Границы:** отказ требует причину; «Перезвонить» без даты не сохраняется;
повторная конверсия того же обращения отвечает «по этому обращению уже создан
заказ»; обращение, закрытое отказом, в заказ не превращается — заводится новое.
