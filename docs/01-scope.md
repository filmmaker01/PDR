# 01. Границы версии 1.0

## Что это за продукт

Telegram Mini App для мастеров PDR (беспокрасочное удаление вмятин) с тремя частями в одном продукте:

1. **Обучение** — курс из трёх последовательных этапов: видеоуроки, материалы, задания с фото/видео, проверка куратором, тесты и практические экзамены, история попыток, автоматическое и ручное открытие этапов, группы (потоки) учеников.
2. **Мастерская (CRM)** — клиенты, автомобили, история обращений, календарь и записи, карточка заказа со статусами и исполнителем, фото «до / в процессе / после», PDR-смета с версиями и скидками, оплаты / предоплаты / возвраты / задолженность, сотрудники с ролями, базовая аналитика.
3. **Платформа** — Telegram-авторизация, изолированные мастерские (workspaces), роли, приватное файловое хранилище, уведомления через бота, закрытый Telegram-клуб с автоматической проверкой доступа, журнал действий, экспорт данных, резервное копирование, веб-админка.

Первая версия должна быть пригодна для реального использования и продажи: ученик проходит курс целиком без участия разработчика, мастер ведёт реальные заказы с деньгами, администратор управляет всем через интерфейс.

## Продукты и доступы

| Продукт | Кому выдаётся | Что открывает |
|---------|---------------|---------------|
| `course` | пользователю (через зачисление в группу) | раздел «Обучение» для конкретного курса |
| `crm` | мастерской (workspace) | раздел «Мастерская» для всех её участников |
| `club` | пользователю | вступление в закрытую Telegram-группу |

Доступы независимы: у каждого свой срок, статус и причина выдачи. Отзыв одного не влияет на другие. Истечение проверяется и фоновой задачей, и при каждом запросе.

## Рабочие правила версии 1.0

Эти правила — осознанные упрощения предметной области, не урезание функций. Они не мешают использовать и продавать продукт, а схема данных не блокирует их снятие позже.

| Правило | Почему | Что заложено на будущее |
|---------|--------|--------------------------|
| Одна мастерская = один филиал | У первых клиентов одна точка; несколько филиалов — это отдельная организационная модель (организация → филиалы → сотрудники) | Мастерская уже изолированная единица; позже над ней добавляется `organization_id` без переписывания CRM |
| Одна валюта на мастерскую | Мультивалютность требует курсов и пересчётов в аналитике | `currency` хранится в мастерской и в каждой смете/оплате |
| Фиксированные роли (ученик, куратор, владелец, сотрудник, администратор) | Гибкий конструктор прав не нужен для первой продажи и усложняет проверку изоляции | Права описаны декларативно в одном месте (`permissions.ts`), роль → набор действий |
| Учёт денег за ремонт вручную | Ремонт — физическая услуга; онлайн-эквайринг и касса — отдельные интеграции с юридическими требованиями | Модель `payment_entries` уже поддерживает способ оплаты, возвраты и корректировки; провайдер добавляется как источник записей |
| Клиент CRM не пользуется приложением | Клиент мастера — запись в базе; ему не нужен Telegram | У клиента есть телефон и `telegram_user_id` (nullable) для будущей онлайн-записи |
| Продажа доступа вне Telegram (ручная выдача) | См. раздел «Что не входит» | `access_grants.reason` и `source` фиксируют, откуда пришёл доступ: `manual`, позже `payment` |

## Что НЕ входит в 1.0 и почему

Ниже только то, что действительно не нужно для полноценной первой версии. Всё остальное из исходного плана включено.

| Функция | Почему не в 1.0 | Что сделано, чтобы добавить позже |
|---------|-----------------|-----------------------------------|
| **Встроенная продажа через Telegram Stars** | Продажа цифровых товаров и услуг внутри бота/Mini App обязана идти через Telegram Stars. Это отдельный платёжный модуль (инвойсы, подтверждение, возвраты, споры) и отдельная бизнес-настройка тарифов. Для продажи первой версии достаточно ручной выдачи доступа после оплаты любым внешним способом — это уже рабочий процесс продажи, а не заглушка | `access_grants` имеет `source` и `external_ref`; модуль `billing` добавится как ещё один источник грантов |
| **Автоматический PDR-калькулятор / оценка по фото** | Нет проверенной методики; неверная автоформула вредит продажам мастера. Правильный путь — собрать реальные сметы из CRM (они структурированы по кузовному элементу, типу, размеру, материалу) и потом строить правила | Позиции сметы уже содержат все характеристики; прайс мастерской — отдельная таблица |
| **Интерактивная схема кузова / 3D** | Чисто интерфейсная надстройка над теми же данными; не меняет ни модель, ни сценарий | `estimate_items.panel_code` — стабильный код элемента, к которому привяжется схема |
| **Онлайн-запись клиентов и внешние календари** | Требует публичного клиентского интерфейса и интеграций (Google/Яндекс); мастер первой версии записывает сам | Записи имеют длительность, исполнителя и защиту от пересечений — та же модель |
| **Зарплаты, проценты, склад, расходники** | Отдельная учётная предметная область (бухгалтерия), не нужна для ведения заказов | Заказ знает исполнителя и согласованную сумму — база для расчёта процентов |
| **Несколько филиалов** | См. рабочие правила | — |
| **Сертификаты, геймификация** | Не влияют на способность учиться и продавать курс | Прогресс и результаты экзаменов хранятся полностью; сертификат — рендер по этим данным |
| **Сложные индивидуальные траектории** | Ручные исключения администратора (`stage_overrides`) закрывают реальные случаи | — |
| **Автопродление клуба по тарифам** | Зависит от встроенных платежей | Срок клуба хранится отдельно и продлевается вручную |

Что из «отложенного» в исходном плане **включено в 1.0**, потому что без этого продукт неполный: несколько курсов в схеме (структурно, без ограничения одним), календарь с переносом записей, сотрудники с ролями и назначением, аналитика, автоматизация клуба, уведомления, экспорт CSV, аудит, резервное копирование, версии сметы, тесты с автопроверкой, конструктор вопросов в админке.

## Критерии готовности версии 1.0

- Ученик самостоятельно проходит этап: смотрит уроки, сдаёт работу, получает возврат на доработку и повторно сдаёт, проходит тест и практический экзамен, видит открытие следующего этапа с понятной причиной блокировки до этого.
- Куратор видит очередь работ своих групп, проверяет, комментирует, принимает или возвращает.
- Мастер проводит реальный заказ: запись → осмотр и фото → смета → согласование → ремонт → фото результата → выдача → оплата с долгом и последующей доплатой.
- Владелец приглашает сотрудника, назначает заказы, видит аналитику за период.
- Администратор выдаёт, продлевает и отзывает доступы к курсу, CRM и клубу; управляет курсом, группами, кураторами; видит журнал действий.
- Пользователь мастерской A не получает данные и файлы мастерской B ни по прямому ID, ни через ссылку на файл.
- Закрытый этап недоступен через прямой запрос к API (видео, задание, экзамен).
- Отзыв доступа действует на существующие сессии.
- Резервная копия восстанавливается на staging по документированной процедуре.
- Mini App работает в Telegram на iOS, Android и Desktop.
