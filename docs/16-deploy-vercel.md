# Публичный staging на Vercel

## Что где живёт

Vercel раздаёт только статику фронтендов. Два проекта, а не три:

| Проект      | Root Directory  | Что это                       |
| ----------- | --------------- | ----------------------------- |
| `pdr-app`   | `apps/miniapp`  | Telegram Mini App             |
| `pdr-admin` | `apps/admin`    | Админка                       |

Третьего проекта `pdr-api` нет намеренно — см. «Почему API не на Vercel».

API, worker, PostgreSQL и файловое хранилище остаются на площадке, где есть
постоянный процесс и диск (подготовленный конфиг — Amvera, `amvera.yml`).

## Как собирается фронтенд

`apps/miniapp/vercel.json` и `apps/admin/vercel.json`:

- `installCommand` и `buildCommand` начинаются с `cd ../..`, потому что это
  pnpm-workspace: приложение нельзя собрать, не собрав сначала `@pdr/shared`;
- `VITE_API_URL=/api` — адрес API относительный. Запросы уходят на тот же
  домен, поэтому не нужен ни CORS, ни `CORS_EXTRA_ORIGINS`, а `connect-src`
  в CSP остаётся `'self'`;
- `--sourcemap false` — карты исходников не выкладываются на публичный адрес;
- `rewrites` отдаёт `index.html` на любой путь, кроме `/api/`, — иначе
  клиентский роутер ломается при перезагрузке страницы;
- `headers` повторяют заголовки безопасности из `infra/nginx/security-headers.conf`.

## Один шаг, который может сделать только владелец аккаунта

Vercel отказывается связывать проект с репозиторием:

> To link a GitHub repository, you need to install the GitHub integration first.

GitHub App Vercel не выдан доступ к `filmmaker01/PDR` (в аккаунте он подключён
только к `filmmaker01/banana-studio`). Установка GitHub App выполняется от
имени владельца репозитория и через API Vercel недоступна.

Что сделать: <https://github.com/apps/vercel> → Configure → аккаунт
`filmmaker01` → Repository access → добавить `PDR` → Save.

После этого проекты создаются автоматически, без участия владельца.

## Куда подключить API

Когда у API появится публичный адрес, в оба `vercel.json` добавляется один
блок перед SPA-правилом:

```json
"rewrites": [
  { "source": "/api/(.*)", "destination": "https://<host-api>/$1" },
  { "source": "/((?!api/).*)", "destination": "/index.html" }
]
```

Пересобирать фронтенд при смене адреса API не нужно: в бандл зашит
относительный `/api`, а не хост.

## Почему API не на Vercel

Vercel выполняет код только как функции, живущие в пределах запроса. Для
текущего API этого мало:

1. **Worker.** `apps/api/src/infra/jobs/worker.service.ts` держит постоянный
   процесс pg-boss с 11 расписаниями (`access-expire` раз в час,
   `appointment-reminders` каждые 5 минут, ночные чистки и проверка бэкапов).
   Между запросами функция не живёт, поэтому ни одно расписание не сработает.
2. **Инициализация очереди в API.** `JobsService.onModuleInit` поднимает
   пул соединений и таймеры pg-boss на каждом холодном старте.
3. **Файлы.** `STORAGE_DRIVER=local` пишет на диск (фото заказов, экспорты,
   PDF смет). На Vercel файловая система только для чтения, кроме временного
   `/tmp`, своего у каждого экземпляра.
4. **Миграции и seed** запускаются из `entrypoint.sh` при старте контейнера —
   у Vercel такого этапа нет.
5. **Секреты.** Переменные окружения проекта Vercel не выставляются через
   доступный MCP-интерфейс, а класть `DATABASE_URL` в репозиторий нельзя.

Минимальное изменение, при котором API поехал бы на Vercel: вынести worker в
отдельный постоянный процесс на другой площадке, перевести хранилище на S3 и
выполнять миграции отдельной командой в CI. То есть база и worker всё равно
живут вне Vercel — и тогда проще держать там же и API.
